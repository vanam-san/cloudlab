# Disaster recovery

Total-loss runbook: the VPS is gone, rebuild everything on a fresh one.
Target: all services back with their data, same domains, new certificates.

## What lives where

Git holds everything needed to rebuild **except** secrets and data:

| Class | Location | In git? |
|---|---|---|
| Service definitions, scripts, docs | this repo | yes |
| Caddyfile, dashboard config | `caddy/Caddyfile`, `glance/config/` | yes |
| Per-service secrets | each `<service>/.env` | **no** — recreate via `run.sh` or restore off-box copy |
| Tailnet allow-list | `caddy/tailscale-ips.caddy` | **no** — recreate from `.example` + your IPs |
| Plane runtime (compose + secrets) | `plane/plane-app/` | **no** — generated by `setup.sh`, holds `plane.env` secrets |
| App data | named Docker volumes (see below) | **no** — snapshot off-box |

Data volumes per service: `umami-db`, `beszel-data`, `postgres-data` +
`redis-data` + `app-storage` (sure), Plane volumes + `plane-app/`,
`checkmk`, `uptime-kuma`, `mongo-data` (checkmate), `caddy-data`
(certificates — re-issuable, see note).

## Routine off-box backup

Run from the repo root on a schedule (weekly is plenty for this scale).
`$DEST` is off-box storage (another machine, S3, USB — anywhere but
this VPS). Secrets go in the same archive; **encrypt it**
(`age`/`gpg`) — it contains every password.

```bash
DEST=/path/to/off-box/cloudlab-$(date +%F)
mkdir -p "$DEST"

# 1. Secrets + generated runtime config (small, critical)
for d in umami beszel glance sure plane caddy checkmk uptime-kuma checkmate; do
  [ -f "$d/.env" ] && cp "$d/.env" "$DEST/$d.env"
done
cp caddy/tailscale-ips.caddy "$DEST/" 2>/dev/null || true
tar czf "$DEST/plane-app.tar.gz" -C plane plane-app

# 2. Data volumes (one tarball each; containers keep running)
for v in umami_umami-db beszel_beszel-data \
         sure_postgres-data sure_redis-data sure_app-storage \
         checkmk_checkmk uptime-kuma_uptime-kuma checkmate_mongo-data \
         caddy_caddy-data; do
  docker run --rm -v "$v:/data" -v "$DEST:/backup" ubuntu \
    tar czf "/backup/vol-$v.tar.gz" -C /data . 2>/dev/null || echo "SKIP: $v"
done
# 3. Plane's own volumes (names vary; list with: docker volume ls | grep plane)
#    plus a database dump per its README (./setup.sh backup).
```

Plane's volume names come from upstream `setup.sh` (e.g.
`plane-app_pgdata`); snapshot each `plane*` volume the same way, or use
`./setup.sh backup` inside `plane/` per its README.

## Rebuild on a fresh VPS

1. Install Docker Engine + Compose v2, clone this repo, `cd` into it.
2. Restore secrets: copy each `$DEST/<service>.env` back to
   `<service>/.env`, `tailscale-ips.caddy` to `caddy/`, and untar
   `plane-app.tar.gz` inside `plane/`.
3. Recreate data volumes from the tarballs (reverse of step 2 above):
   `docker volume create <name>` then untar into it with the same
   ephemeral-container pattern.
4. Start data services first, Caddy last (its config is already in git):
   ```bash
   for s in umami beszel glance sure plane checkmk uptime-kuma checkmate; do
     (cd "$s" && ./run.sh)
   done
   cd caddy && ./run.sh
   ```
   `run.sh` is idempotent and skips init when data exists — on restored
   volumes it just starts and waits.
5. Point DNS (A/AAAA) at the new VPS, uncomment your site blocks in
   `caddy/Caddyfile`, reload Caddy (see root README). Certificates issue
   automatically. Note Let's Encrypt's rate limit (5 duplicate certs per
   week per domain set): a single rebuild is fine; repeated rebuilds in
   one week are not — reuse `caddy-data` from backup when in doubt.
6. Verify each Local URL from the root README table, log into each app,
   confirm data is present.
